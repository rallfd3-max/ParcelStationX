# 可行性分析

## 一、结论

ParcelStationX 作为《软件设计与开发 II》Java 大作业具有较高可行性。

原因是：

- 业务场景真实且容易理解；
- 功能链完整；
- 可以自然覆盖课程要求的 5 项 Java 技术；
- 不需要 SpringBoot 等框架也能完成；
- Swing + JDBC 足以支持课程规模；
- MySQL 数据模型规模适中；
- 可通过模拟通知避免外部短信服务依赖；
- 可以准备稳定的本地答辩环境。

综合判断：**技术可行、时间可控、演示稳定性可保障、课程匹配度高。**

---

## 二、市场场景可行性

快递驿站管理属于典型的小型业务信息化场景。

真实管理工作的核心数据对象相对稳定：

- 快件；
- 收件人；
- 运单；
- 货架；
- 员工；
- 入库/出库事件；
- 异常；
- 通知；
- 统计。

这些对象之间关系清晰，适合关系型数据库。

同时业务中存在明显的信息化价值：

- 减少重复登记；
- 降低查件时间；
- 防止重复出库；
- 记录包裹位置；
- 追溯操作人员；
- 识别滞留件；
- 快速统计业务量。

因此该选题比单纯“学生信息 CRUD”更接近真实管理系统，又不会像电商、支付、社交平台那样涉及复杂分布式架构。

## 三、课程匹配可行性

### 1. 集合

自然用于：

- 临时查询结果；
- 通知任务队列；
- 统计聚合；
- 缓存。

无需为了完成评分而强行增加无业务意义代码。

### 2. 泛型

DAO 层天然适合：

```java
BaseDao<T, ID>
```

同时统一：

```java
Result<T>
PageResult<T>
```

可清晰解释泛型的代码复用价值。

### 3. 序列化

备份元数据、配置快照可以直接使用 Java Serializable。

答辩时容易演示：

- 写文件；
- 读取；
- 恢复；
- serialVersionUID。

### 4. 多线程

Swing 系统必须避免耗时任务阻塞界面。

因此：

- 后台通知；
- 后台备份；
- 后台统计；

都是合理使用线程的场景。

### 5. 数据库编程

快件生命周期本身就需要数据库。

JDBC 可直接体现：

- Connection；
- PreparedStatement；
- ResultSet；
- Transaction；
- rollback；
- commit。

## 四、技术可行性

### Java 17

优点：

- 稳定；
- IDE 支持完善；
- 标准库完整；
- 与 Maven/JUnit/MySQL 驱动兼容。

### Swing

优点：

- Java 原生；
- 无需前后端分离；
- 不需要 HTTP Server；
- 答辩环境简单；
- 与课程“不使用现有业务框架”要求最稳妥。

不足：

- UI 现代感不如 Web。

解决：

- 自定义布局；
- 统一字体、间距；
- CardLayout；
- JTable；
- Java2D；
- 不追求复杂动效。

### JDBC

优点：

- 课程核心；
- SQL 可见；
- 事务机制可答辩；
- 无 ORM 黑盒。

不足：

- 代码量较大。

解决：

- Generic DAO；
- RowMapper 风格接口可自行实现，但不得引入框架；
- 工具类减少重复。

### MySQL

适合：

- 小型关系数据；
- 安装常见；
- SQL 课程兼容；
- 约束、索引、事务都可展示。

## 八、进度可行性

项目采用阶段开发，而不是一次性堆代码。

核心闭环最早在 Phase 5 完成：

```text
登录 -> 入库 -> 库存 -> 查件 -> 出库
```

之后 Phase 6、7 都属于增强。

因此即使后期某个增强模块出现问题，仍有可运行的核心系统。

这大幅降低“到截止日期项目仍无法运行”的风险。

## 九、测试可行性

系统规则明确，可拆成可测试单元。

例如：

- pickupCode 是否唯一；
- parcel 状态是否允许转换；
- shelf 是否超容量；
- 重复 trackingNo 是否拒绝；

- 事务失败是否 rollback；
- backup 是否可反序列化；
- notification queue 是否执行完成。

所以适合 Codex 自动编写并反复运行测试。

## 十一、主要不可行方向与主动规避

### 1. 不做真实短信/微信

原因：

- 需要第三方账号；
- 可能收费；
- 网络不稳定；
- 答辩风险高。

使用模拟通知队列即可展示多线程。

### 2. 不做复杂分布式系统

原因：

- 与课程目标不匹配；
- 增加网络和部署风险。

### 3. 不做前后端分离 Web

虽然 UI 更现代，但后端往往自然滑向 SpringBoot，容易与课程禁用框架要求冲突。

Swing 是更稳妥的课程方案。

### 4. 不使用 ORM

直接 JDBC，技术过程透明。
